# WorkforceComms, NTK, and Context Naming Deep Dive

**Purpose:** Understand WorkforceComms and NTK systems, plus the depth of "context" naming for refactoring

---

## PART 1: WORKFORCE COMMUNICATIONS SYSTEM

### Overview

**WorkforceComms** is a **3-layer email generation system** built to create recurring workforce communication emails (like "Need to Know" newsletters). It's separate from the general "WorkforceStuff" concept.

### The 3-Layer Architecture

#### Layer 1: Product Layer (`WorkforceComms`)
**Purpose:** Stable, reusable product definitions

**Model:** `WorkforceComms`
- `workforceCommsId` (primary key)
- `type` - "email" for now, future-proof for other types
- `name` - "Need to Know", "Urgent Update", "Awareness Email"
- `description` - Optional description
- `companyId`, `originatorId` - Multi-tenant scoping

**Example:**
```typescript
{
  workforceCommsId: "uuid-123",
  type: "email",
  name: "Need to Know",
  description: "Weekly workforce update email"
}
```

**Why it exists:** You create a product once (e.g., "Need to Know"), then generate multiple editions over time.

#### Layer 2: Draft Layer (`WorkforceCommsDraft`)
**Purpose:** Staging container where context and notes live before GPT generation

**Model:** `WorkforceCommsDraft`
- `draftId` (primary key)
- `workforceCommsId` - FK to Product
- `eventRouterIds` - Array of WorkEventRouter references (the work contexts to include)
- `lastEditionId` - Optional reference to previous edition (for "what changed")
- `authorNotes` - Freeform "what to tell GPT"
- `whatChanged` - Crisp delta from last send
- `priorityNotes` - "still a priority", "emphasize X"
- `status` - "drafting" | "readyForGeneration" | "needsReview" | "generating"

**Example:**
```typescript
{
  draftId: "uuid-456",
  workforceCommsId: "uuid-123", // Links to "Need to Know" product
  eventRouterIds: ["router-1", "router-2"], // Work contexts to include
  lastEditionId: "edition-789", // Previous email
  authorNotes: "Focus on the training deadline",
  whatChanged: "New training added, event date moved",
  priorityNotes: "Training is still mandatory",
  status: "readyForGeneration"
}
```

**Why it exists:** You can draft multiple versions, iterate on notes, and then generate when ready.

#### Layer 3: Edition Layer (`WorkforceCommsEdition`)
**Purpose:** Immutable generated emails (final output)

**Model:** `WorkforceCommsEdition`
- `editionId` (primary key)
- `workforceCommsId` - FK to Product
- `subject` - Email subject line
- `body` - Email body (generated by GPT)
- `sentAt` - When email was actually sent (null if draft)
- `companyId`, `originatorId` - Multi-tenant scoping

**Example:**
```typescript
{
  editionId: "uuid-789",
  workforceCommsId: "uuid-123", // Links to "Need to Know" product
  subject: "Need to Know - Week of Jan 20, 2025",
  body: "This week's updates...",
  sentAt: "2025-01-20T10:00:00Z"
}
```

**Why it exists:** Once generated, editions are immutable. You can reference them in future drafts ("what changed since last edition").

### How It Works

1. **Create Product** → "Need to Know" email product
2. **Create Draft** → Link work contexts (eventRouterIds), add notes
3. **Generate Edition** → GPT generates email from draft + contexts
4. **Send Edition** → Mark `sentAt` when actually sent
5. **Next Draft** → Reference last edition, update contexts, generate again

### Key Files

- **Server Actions:** `lib/actions/workforce-comms.ts`
- **API Route:** `app/api/workforce-comms/generate/route.ts`
- **Pages:** `app/workforce-comms/*` (product management, draft creation, edition viewing)

### Relationship to WorkContext

**Important:** WorkforceComms uses `WorkEventRouter` IDs (not WorkContext IDs) in `eventRouterIds`. This is the same router model used by the context system.

## PART 2: NTK (NEED TO KNOW) SYSTEM

### Overview

**NTK** is a **standalone system** for generating "Need to Know" communications in NAVSEA format. It's separate from WorkforceComms (though they share similar goals).

### Architecture

#### Original NTK Model (`NTK`)
**Purpose:** Single NTK document generation

**Model:** `NTK`
- `ntkId` (primary key, mapped to `id` in database)
- `header` - "[TITLE IN ALL CAPS] – [MONTH] [DAY]"
- `poc` - "*POC: [name & email]*"
- `summary` - 2-4 sentence summary in NAVSEA tone
- `sourceText` - Original source text (manual entry, CSV, etc.)
- `draftContent` - Full NTK structure (JSON)
- `metadata` - Additional metadata (isCSV, generatedAt, etc.)
- `companyId`, `originatorId` - Multi-tenant scoping

**Status:** Preserved for backward compatibility

#### New NTK Pipeline (`NTKEdition` + `NTKItem`)
**Purpose:** Batch processing of multiple NTK items from CSV

**Model:** `NTKEdition`
- `id` (primary key)
- `date` - Edition date
- `title` - Edition title
- `companyId`, `originatorId` - Multi-tenant scoping
- `items` - Array of NTKItem[]

**Model:** `NTKItem`
- `id` (primary key)
- `editionId` - FK to NTKEdition
- `inputId` - Stable per-row identifier (e.g., "ntk_${uuid}")
- `rawFields` - Store uploaded CSV row as JSON
- `validated` - Boolean (user validated the row)
- `plainLanguage` - GPT output (plain text)
- `feedback` - For regenerating with user feedback
- `status` - PENDING | VALIDATED | GENERATED | REVIEWED | FINAL

### How It Works

1. **Upload CSV** → Parse CSV rows
2. **Preview Rows** → Validate columns, show preview
3. **Create Edition** → Save rows as NTKItem[] with status PENDING
4. **Generate Items** → GPT generates plainLanguage for each item
5. **Review & Regenerate** → User can provide feedback, regenerate
6. **Mark Final** → Set status to FINAL when approved

### GPT Prompt

The NTK generator uses a specific prompt:
```
Rewrite the following workplace update in clear, concise, plain internal communication ("Need to Know") style.

Do not use emojis or decorative language.
Avoid marketing tone or filler.
Use factual, direct sentences.
Focus on clarity and accuracy.
```

Returns JSON structure:
```json
{
  "header": "[TITLE IN ALL CAPS] – [MONTH] [DAY]",
  "poc": "*POC: [name & email]*",
  "summary": "2-4 sentence summary in plain language",
  "title": "Original title for reference",
  "deadline": "MM/DD/YYYY or null",
  "contactInfo": { "name": "...", "email": "...", "phone": "..." },
  "relatedLinks": ["URL1", "URL2"],
  "tags": ["keyword1", "keyword2"]
}
```

### Key Files

- **Generator:** `lib/services/ntk-generator.ts`
- **CSV Pipeline:** `lib/services/ntk-csv-pipeline.ts` (if exists)
- **Server Actions:** `lib/server/ntk.ts`, `lib/server/ntk-edition.ts`
- **API Routes:** `app/api/ntk/*`
- **Pages:** `app/ntk/*`

### Relationship to Other Systems

**NTK is standalone:**
- Not connected to WorkContext/WorkEventRouter
- Not connected to WorkforceComms (though similar purpose)
- Not connected to WorkOutput (though could be in future)

**Why it exists:** Built as a specific tool for NAVSEA-style communications, separate from the general work context system.

## PART 3: CONTEXT NAMING DEPTH ANALYSIS

### The Naming Confusion

The system has **inconsistent naming** between "context" and "event router". Here's how deep it goes:

### Prisma Schema (Database Level)

**Actual Model Name:** `WorkEventRouter` (NOT `WorkContext`)
```prisma
model WorkEventRouter {
  id         String      @id @default(cuid())
  createdAt  DateTime    @default(now())
  type       ContextType // enum
  eventRefId String      // references typed context model
  companyId  String
  originatorId String
  // ...
}
```

**Typed Context Models:**
- `WorkContextCampaign`
- `WorkContextImpactEvent`
- `WorkContextTraining`
- `WorkContextCommunity`
- `WorkContextBenefits`
- `WorkContextCareer`
- `WorkContextEmployeeCause`
- `WorkEvent` (special case - not "WorkContextEvent")

**Enum:** `ContextType` (not `EventRouterType`)
```prisma
enum ContextType {
  campaign
  impact_event
  training
  event
  community
  benefits
  career
  employee_cause
}
```

### File Naming

**Files with "context" in name:**
- `lib/actions/work-context.ts` ✅
- `lib/actions/typed-contexts.ts` ✅
- `lib/server/context-factory.ts` ✅
- `app/api/context/route.ts` ✅
- `app/api/context/[contextId]/route.ts` ✅
- `app/api/context/create/[type]/route.ts` ✅
- `app/mywork/context/*` (all pages) ✅
- `workcontext-architecture.md` ✅

**Files with "event-router" or "workeventrouter" in name:**
- `lib/actions/work-event-router.ts` ⚠️
- `lib/server/get-work-context.ts` (but uses WorkEventRouter internally) ⚠️
- `docs/WHAT_IS_WORKEVENTROUTER.md` ⚠️

### Function Naming

**Functions with "context" in name:**
- `getWorkContexts()` ✅

- `enrichWorkContext()` ✅
- `createTypedContext()` ✅

**Functions with "event-router" in name:**

### Summary: Naming Depth

| Level | "Context" Usage | "EventRouter" Usage | Status |
|-------|----------------|---------------------|--------|
| **Prisma Model** | ❌ (uses `WorkEventRouter`) | ✅ `WorkEventRouter` | ⚠️ Mismatch |
| **Prisma Enum** | ✅ `ContextType` | ❌ | ⚠️ Mismatch |
| **Typed Models** | ✅ `WorkContext*` | ❌ | ✅ Consistent |
| **File Names** | ✅ Most files | ⚠️ Some files | ⚠️ Mixed |
| **Function Names** | ✅ Most functions | ⚠️ Some functions | ⚠️ Mixed |
| **Variable Names** | ✅ Most variables | ⚠️ Some variables | ⚠️ Mixed |
| **API Routes** | ✅ `/api/context/*` | ❌ | ✅ Consistent |
| **Page Routes** | ✅ `/mywork/context/*` | ⚠️ `/mywork/events` | ⚠️ Mixed |
| **Database Fields** | ❌ | ✅ `eventRefId`, `eventRouterId` | ⚠️ Mismatch |

### The Core Issue

**The database model is `WorkEventRouter`, but everything else uses "context" terminology.**

This creates confusion:
1. Developers see "context" everywhere in code
2. But database uses "WorkEventRouter"
3. Some functions use `workEventRouter` variable names
4. Some functions use `workContext` variable names
5. API routes use "context" but query `WorkEventRouter` table

### Refactoring Considerations

If you want to refactor the naming, you need to change:

**High Impact (Database):**
- Prisma model: `WorkEventRouter` → `WorkContext` (requires migration)
- Database table: `WorkEventRouter` → `WorkContext`
- All foreign key references: `eventRouterId` → `contextId`
- All field names: `eventRefId` → `contextRefId` or `typedContextId`

**Medium Impact (Code):**
- Function names: `getWorkEventRouter()` → `getWorkContext()`
- Variable names: `workEventRouter` → `workContext`
- File names: `work-event-router.ts` → `work-context.ts`
- Type names: Any `EventRouter` types → `Context` types

**Low Impact (UI/API):**
- API routes: Already use "context" ✅
- Page routes: Already use "context" ✅
- User-facing text: Already uses "context" ✅

**Files to Update:**
1. `prisma/schema.prisma` - Model definition
2. `lib/server/context-factory.ts` - Uses `WorkEventRouter` internally
3. `lib/server/get-work-context.ts` - Function name `getWorkEventRouter()`
4. `lib/actions/work-event-router.ts` - Entire file (if exists)
5. `lib/actions/work-context.ts` - Variable names
6. `lib/actions/work-support.ts` - Field references
7. `lib/actions/workforce-comms.ts` - `eventRouterIds` field
8. All API routes that query `WorkEventRouter`
9. All pages that use `workEventRouter` variables

**Migration Strategy:**
1. Create new `WorkContext` model alongside `WorkEventRouter`
2. Migrate data from `WorkEventRouter` to `WorkContext`
3. Update all code to use `WorkContext`
4. Drop `WorkEventRouter` model
5. Or: Rename `WorkEventRouter` to `WorkContext` in single migration (risky)

## PART 4: KEY DIFFERENCES SUMMARY

### WorkforceComms vs NTK

| Aspect | WorkforceComms | NTK |
|--------|----------------|-----|
| **Purpose** | Recurring email generation | NAVSEA-style "Need to Know" docs |
| **Output** | Email (subject + body) | Structured NTK format (header, POC, summary) |
| **Input** | WorkEventRouter IDs + notes | Raw text or CSV rows |
| **Architecture** | 3-layer (Product → Draft → Edition) | 2 models (NTK or NTKEdition + NTKItem) |
| **Integration** | Uses WorkEventRouter for context | Standalone, no integration |
| **Status** | Active system | Active system (both old and new pipeline) |

### Context vs EventRouter

| Aspect | "Context" Terminology | "EventRouter" Terminology |
|--------|----------------------|---------------------------|
| **Database Model** | ❌ (doesn't exist) | ✅ `WorkEventRouter` |
| **Code Usage** | ✅ Most code | ⚠️ Some code |
| **API Routes** | ✅ `/api/context/*` | ❌ |
| **Page Routes** | ✅ `/mywork/context/*` | ❌ |
| **User-Facing** | ✅ "Context" | ❌ |

**Recommendation:** The codebase is mostly "context" terminology. The database model name `WorkEventRouter` is the outlier. Consider renaming to `WorkContext` for consistency.
